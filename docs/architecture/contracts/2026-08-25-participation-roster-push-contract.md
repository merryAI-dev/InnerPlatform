# 참여율 시트 참조 명단 푸시 계약 (초안)

- 날짜: 2026-08-25
- 상태: **초안 - 보람 검토 대기** (승인 전에는 구현하지 않는다)
- 상위 계약: `2026-08-21-participation-sheet-format-contract.md` (좌표·버전·People SSOT 규칙은 그대로 유효)
- 성격: 참조 탭 명단의 신선도는 편의다. 이 계약은 편의를 자동화하되, 무결성 원칙을 한 줄도 양보하지 않기 위한 경계선이다.

## 배경과 문제

채용·퇴사 변동이 잦고, 사업팀은 각자 연동한 시트에서 참여율을 관리한다. 참조 탭은 복사
시점 스냅샷이라 시간이 지나면 낡고, 새 입사자가 드롭다운에 없다. 반영 파이프라인은
라이브 People 로 신원을 해석하므로 데이터는 안 깨지지만, 팀 입장에서는 매번 마찰이다.

## 방향 결정

**People 명단은 플랫폼이 진실(SSOT)이고, 명단은 플랫폼→시트로 흐르는 참조 데이터다.**
참여율 *값*이 시트→플랫폼 단방향인 것과 충돌하지 않는다 - 흐르는 물건이 다르다.
푸시는 숨김 참조 탭의 명단 좌표에만 닿고, `참여율 관리` 탭에는 어떤 경우에도 쓰지 않는다.

IMPORTRANGE(사본마다 승인 클릭, 갱신 불투명)·Apps Script(사본마다 스크립트 버전 드리프트)·
IMPORTDATA(실명 명단이 URL 로 노출) 는 검토 후 기각했다.

## 운영 모델: 연동 = 가입

```
People 변경(채용·퇴사·닉네임/이름 변경)
  → outbox 이벤트 participation.roster.changed (신호만, payload 에 명단 없음)
  → 워커: 활성 프로젝트의 참여율 시트 링크를 spreadsheetId 기준 중복 제거 후 순회
      각 시트: 형식 검증 → 참조 탭 명단 재작성 → 결과 기록
```

- **이벤트는 신호일 뿐이다.** 워커는 실행 시점에 항상 라이브 People 전체를 읽어 쓴다.
  이벤트에 명단을 담으면 순서 꼬임이 생기고, 같은 날 여러 변경은 자연히 1회 반영으로
  합쳐진다(coalesce). 멱등이므로 중복 실행도 무해하다.
- **링크 등록/수정 저장 성공 = 그 시트 1건 즉시 갱신 잡.** 몇 달 묵은 사본을 들고 와도
  연동하는 순간 명단이 최신이 된다. "언제 복사했는가"가 무의미해진다.
- 팬아웃 대상은 활성 프로젝트의 링크로 한정한다. 종료(COMPLETED)와 휴지통(trashedAt)의
  시트는 쓰지 않는다 - 휴지통 시트에 계속 명단(PII)을 보내는 것은 갱신이 아니라 유출이다.
- 재시도·부분 실패는 기존 outbox 정책을 그대로 쓴다. 새 큐를 만들지 않는다. 이벤트
  타입은 outbox 의 `HANDLER_REQUIRED_EVENT_TYPES` 에 등록한다 - 핸들러 없는 실행 경로가
  이 이벤트를 조용히 DONE 처리하면 안 된다.
- 수동 실행 라우트는 `createMutatingRoute`(idempotency 계약)를 탄다 - 같은 키의 재전송이
  새 이벤트를 또 만들면 안 된다.

## 권한: 기존 공유 절차의 상향

지금도 링크를 넣는 자리에서 시스템 계정(`sheetSystemAccount`, `ProjectEditorWizard.tsx`)을
보여주고 **보기 권한** 공유를 안내한다. 이 절차를 그대로 두고 문구만 **편집자 권한**으로
올린다. 새 계정도, 새 절차도 없다.

- 등록/수정 preview 는 읽기 검증에 더해 **쓰기 가능 여부를 검증**한다. 권한이 모자라면
  저장 전에 그 자리에서 "편집자로 공유해 주세요"로 안내된다 - 오류가 난 뒤에 알려주면 늦다.
- 기존 링크(보기 권한만 공유된 시트)는 등록을 소급 차단하지 않는다. 푸시가 권한 실패로
  기록되고 상태 화면에 노출되면, 팀이 편집자 공유를 추가하는 것으로 합류한다.
- Sheets API 스코프는 이미 `auth/spreadsheets`(읽기·쓰기 겸용)이고 쓰기 헬퍼
  `batchUpdateValues` 도 이미 있다. 새 스코프·새 자격증명 없음. AXR 에는 "서비스 계정이
  참여율 시트의 숨김 참조 탭을 갱신하게 된다"는 운영 공지만 하면 된다.

## 쓰기 규칙 - 읽기와 같은 원칙

1. **쓰기 전 `참조!F1` 을 읽고 검증한다.** 아는 버전(`MYSC-PARTICIPATION-V1`/`V2`)이면
   그 버전의 참조 명단 좌표에만 쓴다. 모르는 형식은 적응하지 않고 건너뛰며 실패로 기록한다
   ("양식이 다릅니다" 원칙의 쓰기판).
2. **닿는 범위는 참조 탭 명단 열(A: 닉네임, B: 이름)뿐이다.** `참여율 관리` 탭, 참조 탭의
   월 목록(D열)·형식 마커(F1)에는 쓰지 않는다.
3. **병합-보존 재작성, 멱등.** 최종 명단 = 라이브 People ∪ (시트에만 있는 기존 행,
   자리표시자 제외, 시트에 적힌 이름 그대로) + `미정-1~10`. 시트에 있는데 라이브 People 에
   없는 닉네임(개명·삭제·과거 스냅샷)을 **지우면 과거 급여 행의 이름 조회가 끊긴다** -
   행 수 가드는 같은 수의 교체(개명)를 못 잡으므로, 보존이 append-only 를 실제로 강제하는
   장치다. 범위 전체를 한 번에 다시 쓴다(부분 갱신 없음). 구양식의 `채용예정-N` 행도
   보존한다 - 시트 데이터가 참조할 수 있다.
4. **RAW 로 쓴다.** `USER_ENTERED` 는 People 의 이름·닉네임에 `=` 가 섞이면 시트에서
   수식으로 실행되는 주입 경로다. 명단 값은 언제나 텍스트다.
5. **가드 두 겹.** ① 라이브 People 이 0명이면 `people_empty` 거부 - 자리표시자는 항상
   10개가 붙으므로 "행이 있다" 로는 빈 조회(테넌트 오설정)를 못 잡는다. ② 병합 결과가
   기존 행 수보다 적으면 `roster_shrunk` 거부 - 병합 구조상 불가능하지만 마지막 안전핀.
6. **오류 분류가 재시도를 결정한다.** 재시도(`api_error`)는 일시 장애만: 408/429/5xx/
   상태 없음(네트워크). 401/403 은 `permission_denied`, 404 는 `not_found`, 그 외 4xx 는
   `request_rejected` - 사람이 고칠 문제를 outbox 가 8번 반복하면 쿼터만 탄다.
7. V1 사본도 참조 명단 좌표가 같으므로 갱신한다. 단 V1 드롭다운 검증 범위(`$A$2:$A$97`
   고정) 확장은 이 계약의 범위 밖이다(아래 비범위).
8. **닉네임 불변 강제는 People 쪽 숙제로 남아 있다.** 이 계약의 보존 규칙은 시트가
   깨지는 것을 막을 뿐, People 에서 닉네임을 바꾸면 그 사람의 과거 행은 ingest 에서
   연결 대기로 빠진다. persons 저장 경로의 닉네임 변경 차단(또는 이력 유지)은 codex 구역
   랜딩 후 별도 PR 로 다룬다.

## 실패 노출: ID 가 아니라 이름으로

시트별 푸시 상태를 기록하고 관리 화면에 보여준다. 표시는 **매핑된 시트 제목 + 프로젝트명**
이다. spreadsheetId 는 진단용으로 저장만 하고 화면에 앞세우지 않는다 - 운영자가 ID 를 보고
어느 시트인지 알 수 없다.

- 기록 단위: spreadsheetId 별 { 시트 제목, 연결된 프로젝트명(들), 최종 성공 시각,
  마지막 실패 사유(권한 없음/형식 다름/행 수 감소 거부/API 오류) }.
- 시트 제목은 등록 preview 때 받아 저장하고(제목 조회는 기존 Drive metadata 경로 재사용),
  푸시 성공 시마다 최신화한다 - 팀이 시트 이름을 바꿔도 따라간다.
- 실패는 조용히 쌓이지 않는다. "왜 우리 시트엔 새 사람이 안 떠요?"라는 문의가 왔을 때
  보는 곳이 이 화면이다.

## 구현 배치 - 충돌 경계 (중요)

`server/bff/routes/projects.mjs` 와 `src/app/components/projects/ProjectEditorWizard.tsx` 는
현재 다른 세션(codex)의 연속 작업(#655~#663, `fix/project-info-draft-open-legacy-pending`)과
겹친다. People 쪽도 `feat/people-professional-profile-v2` 가 진행 중이다. 따라서:

**신규 파일 (충돌 없음, 먼저 구현 가능):**

| 파일 | 내용 |
|---|---|
| `server/bff/participation-roster-push.mjs` | 명단 구성(빌더와 공유), 형식 검증, 참조 탭 재작성, 행 수 가드 |
| `server/bff/participation-roster-push.test.mjs` | 계약 규칙 전부를 고정하는 테스트 (형식 거부·행 수 감소 거부·멱등) |
| `server/bff/routes/participation-roster-status.mjs` | 푸시 상태 조회 라우트 (시트 제목·프로젝트명 매핑 포함) |
| 워커 등록 | 기존 work-queue 워커에 잡 타입 추가 - 새 프로세스·새 크론 없음 |

**기존 파일 최소 훅 (codex 작업 랜딩 후, 마지막에 각각 소규모 PR 로):**

| 파일 | 변경 | 크기 |
|---|---|---|
| `ProjectEditorWizard.tsx` | 공유 안내 문구 "보기"→"편집자" | 문구 1곳 |
| projects 라우트의 preview 검증 | 쓰기 가능 검증 호출 1곳 + 시트 제목 저장 | 함수 호출 1곳 |
| People 저장 경로 | outbox enqueue 훅 1곳 (`people-professional-profile` 랜딩 후 위치 확정) | 호출 1곳 |

명단 구성 로직은 `scripts/build-participation-sheet-template.mjs` 의 것과 **한 곳으로
모은다**(빌더가 새 모듈을 import). 만드는 쪽과 미는 쪽이 다른 명단을 쓰기 시작하면 그게
드리프트의 시작이다.

## 안전망 - 실패해도 지금보다 나쁘지 않다

푸시가 어떤 이유로든 실패하면 그 시트의 드롭다운이 낡을 뿐이다. 반영은 변함없이 라이브
People 로 해석하고, 미정-N·이름 승격·연결 대기·등록 후보 경로가 그대로 받친다. 이
자동화의 최악의 경우가 "현재 상태"다. 급여 데이터의 무결성은 이 계약 이전과 이후가 같다.

## 명시적 비범위

- 참여율 값·기간·역할 등 `참여율 관리` 탭에 쓰는 것 일체.
- V1 사본의 드롭다운 검증 범위 확장(batchUpdate/setDataValidation). 값 쓰기보다 침습적이라
  별도 결정으로 미룬다. V2 양식 자체의 검증 범위 상한 점검도 같이 다룬다.
- People 자동 등록. 상위 계약 그대로 - 사람이 등록하고 파이프라인은 잇기만 한다.
- .xlsx 파일 사본 갱신. 원격 갱신 수단이 없다. 연동 관리하는 시트는 구글 시트로 통일한다.
- IMPORTRANGE 등 당기기(pull) 방식 병행. 경로는 하나만 둔다.
